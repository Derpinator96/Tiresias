## Decisions

- 2026-10-03: OllamaChat in agent/llm.py calls POST /api/chat with stream false. Relied on, read 2026-10-03: https://github.com/ollama/ollama/blob/main/docs/api.md ("Generate a chat completion": messages with role system, user, assistant or tool; `format` as `json` or a JSON schema, with the structured-outputs example; `options` such as temperature and num_ctx; non-streaming response `message.content`, `done_reason`, `prompt_eval_count`, `eval_count`; errors as {"error": ...}), https://docs.ollama.com/api/chat (same fields), https://docs.ollama.com/faq (default context 4096, num_ctx per request, OLLAMA_HOST, OLLAMA_NO_CLOUD), https://docs.ollama.com/linux (install, systemd unit with Restart=always and RestartSec=3, `systemctl edit ollama`).
- 2026-10-03: gemma2 has no tools capability on ollama.com, so Ollama's `tools` parameter is not used. The 8 tools are listed in the system prompt, and `format` constrains every reply to {"name": one of the 8 tools or "final_answer", "args": object, "answer": string}. The reply maps onto the same Gemini-shaped content the loop already uses (functionCall or text part), so agent.py, the number checker and the ledger path are unchanged.
- 2026-10-03: gemma2:2b's Ollama template (ollama.com/library/gemma2:2b, template blob e0a42594d802) renders only user, system and assistant messages; a `tool` message would be silently dropped. Tool results therefore go back as user messages, "Result of tc_xxxxxxxx (tool): <compact JSON>", so the model sees the ID it must cite.
- 2026-10-03: context. gemma2's context is 8192 tokens and its tokenizer splits digits (Gemma 2 report, arXiv 2408.00118). Ollama's default num_ctx is 4096, so options.num_ctx is set from llm.ollama.num_ctx on every request. Ollama trims the oldest messages silently when a chat does not fit, which could drop the tool results an answer cites, so OllamaChat refuses to send instead (ContextOverflow, /ai/ask 503): estimated prompt tokens (each digit one token, other characters at llm.ollama.chars_per_token = 2.5) plus llm.ollama.num_predict (768) must fit num_ctx. After a reply, prompt_eval_count + eval_count reaching num_ctx also raises (a partial check: with Ollama's prompt cache prompt_eval_count can count only new tokens). Nothing is truncated by our code.
- 2026-10-03: measured on the bt-airgap stack (10,000,000 sales rows), through the real tools and gateway, with the scripted stand-in (infra/tests/fake_ollama.py), no LLM: the Q1 sequence get_slow_templates, get_plan, mine_candidates, run_rl, simulate grows the prompt from 3,367 to 8,136 characters (estimated 1,368 to 3,751 tokens). Compact JSON result sizes: get_slow_templates 1,668, get_plan 757, mine_candidates 1,474, run_rl 342, gnn_explain 497, rewrite_candidates 778, verify 393 characters. A worst case of 8 calls (two plans and two gnn_explain) is 12,211 characters, estimated 5,693 tokens, plus 768 for the reply: 6,461 of 8,192. The estimate is an assumption until a real run's "prompt tokens evaluated" events calibrate it.
