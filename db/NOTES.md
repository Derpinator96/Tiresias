- 2026-10-03: twin parameter mapping by frequency rank. The twin replaces every most-common value from `pg_stats` with a synthetic value of the same type that keeps the original's frequency. A replayed query's filter value therefore has to be translated before it runs on the twin, or `region_id = 7` would hit a twin value with a different frequency. The mapping is built on the private side only: for each column, sort production's most-common values by frequency and the twin's synthetic values by the same frequencies, and pair them by rank. A production value of rank k maps to the twin value of rank k. Values outside the most-common list (numbers and dates sampled inside histogram buckets) are passed through unchanged, because bucket sampling keeps the same value range. The mapping is never sent across the boundary. To be implemented in step 10.

- 2026-10-03: how a pair is sampled. Every column sampler now draws from one uniform u per row, and each bucket (most-common value, equi-depth histogram bucket, or the rest) owns an interval of u (`draw.intervals`). For a pair (first, second), pg-prod counts rows by (first column's bucket, second column's bucket) in one GROUP BY (`_joint`; only counts leave the query). The twin then draws the second column's bucket given the first column's bucket and places u inside that bucket's interval (`_conditional_u`). Values stay synthetic: the same rank map and histogram sampling as an unflagged column. The first column is bucketed by its most-common values only, with the rest as one bucket (ponytail comment in `_first_keys`). A pair whose second column is a primary key is flipped. A primary key first column (stores.store_id) is bucketed through the largest child foreign key's rank map (sales.store_id), because twin parent ID k stands for the parent of rank k there. Joint queries on pg-prod took 0.0 s, 1.9 s and 2.6 s; `make twin` took 1 min 43 s wall.

- 2026-10-03 (step 32): partition measurement (`db/sandbox/twin_measure.py`, step 6 of its docstring). Choice: the replayed after-queries are pointed at a partitioned copy (`retarget`, sqlglot, the old name kept as alias) instead of renaming tables. The real table is never renamed, locked for writes or changed, so a crash cannot leave the twin or pg-prod without `sales`; restoring is `DROP TABLE` of the copy (finally block, and again before each build). The copy: `LIKE ... INCLUDING DEFAULTS INCLUDING CONSTRAINTS`, `PARTITION BY RANGE (col)`, one partition per month from min to max of the column plus a default, `INSERT ... SELECT *`, primary key extended by the partition column (Postgres requires it), the table's own foreign keys (so inserts pay the same reference checks), `VACUUM ANALYZE`. Foreign keys that reference the table (returns.order_id) stay on the real table. Indexes of the configuration on that table are built on the copy. Storage delta = copy total size (heap, indexes, TOAST over all partitions) minus the table's, plus indexes on other tables. Write cost: pgbench inserts into the copy for the after phase; source rows always come from sales, so the read part of each insert is equal (`write_cost.insert_ms(conn, table)`).
